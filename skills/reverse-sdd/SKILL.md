# Reverse-SDD: from repository to rebuild-ready specs

Turn an existing repository (code + git history) into a complete, traceable documentation
kit that is good enough to rebuild the system from scratch. The kit has seven artifacts:

```
docs/reverse-sdd/
├── 00-INVENTORY.md             # Raw findings (generated by scripts, then curated)
├── 01-ARCHITECTURE.md          # Architecture: components, flows, decisions
├── 02-TECH-STACK.md            # Languages, frameworks, infra, versions
├── 03-EVOLUTION.md             # Timeline of the system derived from git history
├── US/
│   ├── US-INDEX.md             # Index + traceability matrix (US ↔ commits ↔ tests)
│   └── US-001-<slug>.md ...    # One user story per feature cluster, with
│                               #   acceptance criteria + test cases
├── 04-TEST-MATRIX.md           # Consolidated test-case matrix
└── 05-REBUILD-PLAN.md          # Rebuild plan, mapped to SDD artifacts
```

## The two ground rules (read these first)

1. **Traceability or it doesn't exist.** Every non-trivial claim must carry evidence:
   architectural claims cite `[VERIFY: path/file.ext:line]`; historical claims and every
   user story cite commit hashes `[COMMITS: abc1234, def5678]`. If you cannot point to
   code or a commit, mark the statement `[INFERRED]` and say why. A plausible-looking spec
   that diverges from the code is worse than no spec — the rebuild will inherit its errors.

2. **The git history is a first-class source, not decoration.** The code tells you *what*
   the system is; the history tells you *in what order it became that*, which fixes were
   painful (those become acceptance criteria), and which features cluster together (those
   become user stories). Always run the history analysis before writing user stories.

## Workflow

Work through the phases in order. Phases 0–1 are script-driven and cheap; run them first,
always. For a quick assessment the user may only want Phases 0–2; confirm scope if unclear.

### Phase 0 — Inventory (scripts, ~1 min)

```bash
python3 scripts/repo_inventory.py /path/to/repo -o /path/to/repo/docs/reverse-sdd/analysis
python3 scripts/git_history.py    /path/to/repo -o /path/to/repo/docs/reverse-sdd/analysis
```

This produces `inventory.json` / `inventory.md` (stack detection) and `history.json` /
`history.md` (commit clusters, eras, hotspots, contributors). Read both `.md` summaries.
If the repo has no `.git` directory, `git_history.py` will fail: tell the user the
evolution/user-story phases need the real repository (not an export) and continue with
what exists.

If the repo has a `.codegraph/`, `graphify-out/`, or `lat.md/` directory and the
graph-first-context skill is available, use it for Phase 2 exploration instead of raw
file reading — it is dramatically cheaper.

### Phase 1 — Curate the feature clusters

Open `history.json`. The script groups commits into clusters by conventional-commit scope,
falling back to the dominant top-level directory. Machine clustering is a draft, not truth:

- Merge clusters that are one feature split across scopes (e.g. `auth` + `login`).
- Split clusters that mix unrelated work under a generic scope (`core`, `misc`, `src`).
- Discard pure-noise clusters (formatting, dependency bumps) from user-story generation,
  but keep them in the evolution timeline.
- A good cluster answers: "what user- or system-visible capability did this build?"

Record your final cluster list in `00-INVENTORY.md` with the commit hashes each contains.

### Phase 2 — Architecture (`01-ARCHITECTURE.md`)

Read `references/architecture-template.md` and fill it. Explore the code top-down:
entrypoints → routing/controllers → services/domain → persistence → integrations.
Every component, flow and decision cites `[VERIFY: file:line]`. Where the history shows a
refactor (cluster with type `refactor` and high churn), document the *current* design and
note the superseded one in a "Historical decisions" subsection — rebuilds should not
re-walk dead ends.

### Phase 3 — Stack (`02-TECH-STACK.md`)

Read `references/tech-stack-template.md` and fill it from `inventory.json` plus manifests.
Pin exact versions from lockfiles when available. Flag anything EOL/deprecated in the
"Rebuild risks" table — the rebuild is the moment to replace it.

### Phase 4 — Evolution (`03-EVOLUTION.md`)

Read `references/evolution-template.md`. Use the eras from `history.json` (tag-based, or
quarter-based when untagged). For each era write what capability the system gained, citing
the clusters and representative commits. This is a narrative, not a log dump: 5–15 lines
per era. Close with "Lessons for v2": recurring fix patterns (same file fixed 4+
times = design smell), abandoned directions, hotspot files from the script output.

### Phase 5 — User stories (`US/US-NNN-*.md`)

For each curated cluster, read `references/user-story-template.md` and produce one user
story file:

- Reconstruct the intent: "As a / I want / So that" inferred from commit messages, the
  code the commits touch, and tests they added. Mark the persona `[INFERRED]` if the
  commits don't reveal it.
- **Acceptance criteria in Gherkin** (Given/When/Then). Sources, in priority order:
  (1) existing tests in the repo — each meaningful test is a criterion, cite the test
  file; (2) fix commits within the cluster — every bug fixed is a criterion the original
  story missed, phrase it as the behavior the fix enforces, cite the fix hash;
  (3) validation/error-handling code paths.
- **Test cases**: derive at least happy path + edge + negative per criterion, in the
  table format the template defines. Reuse real test names where they exist.
- Number user stories in rough chronological order of their clusters (US-001 = earliest).

Then write `US/US-INDEX.md`: one row per user story with cluster name, commit count,
hashes range, and links. Aim for the smallest set of user stories that covers all
non-noise clusters — typically 8–25 for a mid-sized repo. If it's heading past ~30, your
clusters are too fine.

### Phase 6 — Test matrix (`04-TEST-MATRIX.md`)

Consolidate all test cases from the user stories into one matrix: ID, user story,
criterion, type (unit/integration/e2e), priority (P1 = protects a behavior that a fix
commit shows was once broken), and whether an automated test already exists in the
current repo (cite it) or must be written for v2.

### Phase 7 — Rebuild plan (`05-REBUILD-PLAN.md`)

Read `references/rebuild-plan-template.md`. Order the user stories into build phases by
dependency (persistence/auth before features that need them — the original chronology in
`03-EVOLUTION.md` is a strong hint). If the **spec-driven-design** skill is available,
generate its artifacts (PRD, API Spec, Technical Design, Data Model, Implementation Plan)
using the reverse-engineered docs as input and say so in the plan; otherwise, the plan's
"Pending SDD artifacts" table tells the user which to produce next.

## Validation pass (always, before delivering)

1. Pick 5 random `[VERIFY: file:line]` citations and re-open the files. Wrong line → fix
   all citations from that document, not just the sampled one.
2. Pick 3 user stories and confirm each cited commit hash exists
   (`git show --stat <hash>`) and actually belongs to that feature.
3. Cross-check coverage: every non-noise cluster in `00-INVENTORY.md` appears in exactly
   one user story; every user story appears in `04-TEST-MATRIX.md` and in a phase of the
   rebuild plan.
4. Count `[INFERRED]` marks. More than ~20% of claims inferred → tell the user which areas
   of the repo were too opaque and what would resolve them (a domain expert, missing docs,
   runtime access), rather than papering over it.

## Scaling to large repos

For repos with >2,000 commits or >200k LOC: cap history with
`git_history.py --max-commits 2000` (most recent) plus a second pass `--until <date>` for
the early era if needed; document architecture per top-level module in separate sections;
and propose to the user splitting user-story generation per module across sessions. Never
silently truncate — state what was and wasn't analyzed in `00-INVENTORY.md`.
